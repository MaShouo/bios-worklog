# BIOS Worklog 工作方法

## 核心原则

所有有信息增益的动作都属于调查进展，包括：

- 新发现或新现象；
- 一个实验成功；
- 一个实验失败；
- 排除或降低某条路径的优先级；
- 缩小复现条件；
- 推翻旧假设或建立新假设；
- 找到相关代码、寄存器、规范或提交；
- 修改代码、编译、刷写和验证；
- 因缺少设备、日志或权限而被阻塞。

因此只使用统一的 `checkpoint`，不把“失败尝试”另设成低价值记录。

## 一个高质量检查点回答四个问题

1. **为什么做？** 当时的证据或假设是什么？
2. **做了什么？** 代码、命令、日志、硬件配置或实验步骤是什么？
3. **结果是什么？** 现象是否改变，数据如何变化？
4. **接下来怎么走？** 该结果如何改变判断和下一步？

失败实验应写清楚适用边界。例如：

> 修改 Graphics OpRegion 后复现率仍为 10/10。这削弱了“OpRegion 内容错误是直接根因”的假设，但没有排除 Resume 初始化时序问题；若 PCI Restore 方向无结果，可结合执行时序重新检查。

不要简单写成：

> 修改无效。

## 事实、判断与结论

- **已确认事实**：日志、源码、寄存器 dump、可复现实验或测试结果直接支持。
- **当前判断**：用于指导下一步的解释，应标注置信度。
- **尚未确认**：仍需验证的关键问题、风险和边界条件。
- **最终根因**：能解释现象，并由修复及验证形成闭环。

“补丁后单次没有复现”通常只能进入 `verifying`，不能自动等价为根因已确认。

## 建议生命周期

```text
start
  ↓
checkpoint × N
  ├─ pause → resume → checkpoint
  ├─ verifying → checkpoint
  └─ solve
       ↓
     reopen（同一问题再次出现时）
```

## 跨会话恢复

恢复时以问题文件中的以下内容为权威：

1. 问题描述和环境；
2. 当前状态；
3. 最近若干检查点；
4. 下一步；
5. 原始文件路径。

无需恢复整段 AI 聊天。若记录与新证据冲突，以新证据为准，并创建检查点解释冲突。

## 何时提醒保存检查点

`status` 中的 `checkpointRecommended` 表示距离文件上次更新超过配置阈值，仅用于提醒“可能有尚未保存的调查”。它不判断用户是否有进展。

适合提醒的时机：

- 一轮实验或分析结束；
- 准备开始另一条调查路径；
- 准备切换任务或会话；
- 用户询问接下来做什么。

不适合提醒的时机：

- 命令仍在运行；
- 用户正在连续提供日志；
- 刚刚拒绝过提醒；
- 没有任何新增调查内容。

## 敏感信息

默认不要记录：

- 密码、API Token、私钥、签名密钥或密钥材料；
- 不必要的内网地址、账号、客户身份和设备序列号；
- 与问题无关的完整聊天或完整构建日志。

优先记录摘要、必要证据和本地附件路径。遵守用户所在组织的数据分类和保密规则。
