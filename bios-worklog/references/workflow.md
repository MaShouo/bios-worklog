# BIOS Worklog 工作方法

## 两类记录

### Issue

适合异常、Bug、兼容性或稳定性问题。目标是形成：

```text
现象 → 证据 → 根因 → 修复 → 验证
```

### Feature

适合新功能、技术方案和可供其他项目参考的实现过程。目标是形成：

```text
目标/约束 → 方案选择 → 实现过程 → 验证 → 复用指南
```

创建入口故意拆成 `start-issue` 与 `start-feature`，用户无需手动输入长类型参数和描述；Agent 从当前对话提取正文。

## 所有信息增益都是进展

包括：新发现、成功/失败实验、排除路径、需求澄清、候选方案比较、设计决策、方案调整、代码实现、验证和阻塞原因。因此统一使用 `checkpoint`。

一个高质量检查点回答：

1. 为什么做？
2. 做了什么？
3. 结果是什么？
4. 它如何影响当前判断或方案？
5. 下一步是什么？

失败实验不要只写“无效”，而要说明削弱/排除了什么、适用边界及何时值得重试。

## 功能方案的复用价值

为了让别的项目能够参考，功能完成时至少整理：

- 最终设计与选择原因；
- 公共模块和项目适配层的边界；
- 修改文件/模块和接口；
- 验证范围及异常场景；
- 可直接复用部分；
- 项目相关部分；
- 复用前提和不适用情况；
- 参考实现步骤；
- 已知限制和风险。

跨项目参考不需要专门的 `adapt` 命令：

1. `context <源记录ID>` 只读加载旧方案；
2. 在目标项目执行 `start-feature`；
3. 新记录通过 `related_records` 关联源 ID；
4. 目标项目保留自己的 checkpoint 和验证结果。

## 事实、判断与完成条件

- 已确认事实：由日志、源码、寄存器、实验或测试直接支持。
- 当前判断/方案：指导下一步，允许后续推翻。
- 尚未确认：关键风险、边界和待验证内容。
- `solve`：问题根因、解决方法和验证闭环。
- `complete`：功能最终方案、验证结果和可复用部分均已明确。

单次不复现不能自动等于问题解决；功能代码写完但未验证也不能自动等于完成，可先进入 `verifying`。

## 生命周期

```text
start-issue  → checkpoint × N → pause/resume → solve → reopen（可选）
start-feature → checkpoint × N → pause/resume → complete
```

已完成的功能作为不可变参考。后续项目应创建自己的功能记录，不修改源项目历史。

## 跨会话恢复与提醒

恢复上下文只需要：记录基础内容、当前状态、最近检查点、下一步和原始路径，不复制完整 AI 聊天。

`checkpointRecommended` 只表示距离上次保存超过阈值，不判断用户“没有进展”。在自然停顿点询问一次即可；用户拒绝后不要反复提醒。

## 敏感信息

不要记录密码、Token、私钥、签名密钥、个人数据、不必要的客户身份、设备序列号或内部地址。大日志只记录摘要和附件路径，并遵守组织的数据分类规则。
